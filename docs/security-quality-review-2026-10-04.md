# GIST — Security & Quality Review of M6 (2026-10-04)

**Role:** M6 R7 (independent review). **Reviewed tip:** `integration/m6-2026-10-03` @ `6cb848d`. **Review branch:** `worktree-agent-aa9c754bbe67f3665` (reviewer commits on top of `6cb848d`).
**Method:** as in `docs/security-quality-review-2026-09-29.md` / `docs/security-review-v2.md`: claims were re-derived from source and by running commands, not taken from `CLAUDE.md` or role reports. Anything not run is listed in §9.

## 1. Executive summary

M6 (PDF import on pinned pdfium, `Block::Table` + IR v2, PDF UI + scanned-PDF OCR fallback) is in good shape. No High/Medium defect was found. The supply-chain pin is genuinely enforced (the pinned SHA-256 matched a fresh download), the dev-only library-path fallbacks are genuinely compiled out of the shipped Rust core, every limit check I traced runs before the allocation it guards, and ADR-019's forward-compat claim is backed by real tests.

Two real (low-severity) defects were found, proven with a test or script, and fixed in this review: a heading-level `u8` wrap in `gist-parse-pdf` (F31) and a NaN pixel size in `PdfPageRenderer.pixelSize` (F32). Four further low/informational findings are reported, not fixed (F33–F36). The CLAUDE.md claim that `gist-model` compiles to `wasm32-unknown-unknown` was false and is now fixed (F37), and F29's `BSD-2-Clause` allow-list entry was pruned.

## 3. pdfium as a native dependency (checklist 1)

**Pin enforcement.** `tools/fetch-pdfium.sh:15-17` pins tag `chromium/8076`, asset `pdfium-mac-univ.tgz`, SHA-256 `3bdb93e2...bdc1`. I ran `./tools/fetch-pdfium.sh` against the live release: it downloaded and printed "verified and extracted" (the script exits 1 on mismatch, lines 40-46, before `rm -rf`/extract, so it fails closed). The only fetchers are: the script itself, the Xcode pre-build script in `apps/apple/project.yml` (calls the same script), and `apple-build.yml`/`core-test.yml` (macOS)/`fuzz.yml` (all call the same script). There is no second download path, so no build can silently use a different binary — except the stamp short-circuit (F34a): `.pinned-sha256` plus file existence skips re-hashing, so a locally replaced dylib under `artifacts/pdfium/` would be embedded. `artifacts/` is gitignored; CI starts clean, so this is a local-dev-only exposure.
- TLS: `curl --fail --proto '=https' --tlsv1.2 --location`. Initial URL is https; redirect hops are not restricted by `--proto` (F34b). I confirmed the GitHub URL 302s to `release-assets.githubusercontent.com` over https.
- Extraction: `tar -xzf` with no `-P`; bsdtar rejects `..`/absolute paths by default. I inspected the result: `find artifacts/pdfium -type l` empty, 45 regular files, everything under `artifacts/pdfium/` (`lib/`, `include/`, `licenses/`, `LICENSE`, `VERSION`, `args.gn`, `PDFiumConfig.cmake`). I did not capture a `tar -t` listing of the raw archive (a tool-guard blocked the command), so traversal entries that bsdtar silently skipped would not show; the post-extraction tree is what I can vouch for.
- Binary facts: `lipo -info` = x86_64 + arm64; `args.gn` shows `pdf_enable_v8=false`, `pdf_enable_xfa=false` (no JavaScript/XFA attack surface), `is_debug=false`; the upstream signature is ad-hoc/linker-signed (`codesign -dv`), install name `./libpdfium.dylib` (irrelevant because it is loaded by absolute path).

**Library loading.** `crates/gist-parse-pdf/src/pdfium_backend.rs:62-81` `candidate_paths()`: configured path (`set_library_path`, which is **not** exported over FFI — grep over `crates`/`apps` finds no caller), `<exe>/../Frameworks/libpdfium.dylib`, `<exe dir>/libpdfium.dylib`, and, only under `#[cfg(debug_assertions)]`, `$GIST_PDFIUM_LIBRARY` and the baked-in `CARGO_MANIFEST_DIR/../../artifacts/pdfium/lib`. The shipped core is built by `tools/build-core-xcframework.sh:15-18` with `cargo build -p gist-ffi --release`, and the workspace `[profile.release]` does not set `debug-assertions`, so the env var and baked build path are compiled out of the app. Nothing is loaded relative to the cwd (all candidates are absolute, derived from `current_exe()`), so a hostile cwd cannot inject a library. A missing/unloadable library is the typed `PdfError::LibraryUnavailable` (path logged at `debug!` only; the message returned is a fixed string).

**Containment and signing (N8).** `bind()` only creates a `Pdfium` handle after a successful first bind (the `Pdfium::default()` panic/hang trap is avoided). `#![forbid(unsafe_code)]` holds in this crate, but pdfium-render and pdfium itself are unsafe/C++; there is no process isolation (F33). `project.yml:68-71` embeds the dylib with `embed: true, link: false, codeSign: true`; `ENABLE_HARDENED_RUNTIME: YES` (`project.yml:18`); `GISTmacOS.entitlements` holds only app-sandbox, user-selected read-write, network client (no `disable-library-validation`). Because the entitlements are unchanged, a sandboxed app that dlopen()s an in-bundle dylib signed with the app's own identity is consistent. **Unverified:** no signing identity exists here, so a real signed Hardened-Runtime launch loading `libpdfium.dylib` has not been done; the release checklist now carries that step (§8).

## 4. gist-parse-pdf limits and layout (checklist 2)

Ordering (`crates/gist-parse-pdf/src/lib.rs`, `pdfium_backend.rs`): `max_bytes` checked first (`lib.rs` size gate) -> `%PDF-` magic in first 1024 bytes -> pdfium load (parsing of xref/objects happens inside pdfium here and cannot be pre-limited) -> encryption/permission check (`can_extract_text_and_graphics`, rejects restricted docs as `Encrypted`; no password is ever tried) -> `max_pages` checked on `doc.pages().len()` **before any page is loaded** -> per page, pdfium's reported char count `n` is compared against `MAX_GLYPHS_PER_PAGE` (2,000,000) and the remaining `max_expanded_bytes` budget **before** `glyphs.reserve(n)` -> cumulative `text_bytes` re-checked after each page's lines, and once more in `build_document`. Zero text yields `NoTextLayer` (`layout.rs` `hist.is_empty()` / `events.is_empty()`); encrypted yields `Encrypted`. Tests in `lib.rs` (`page_count_bomb_rejected_before_any_page_loads`, etc.) and the real-pdfium fixture tests pass (`GIST_REQUIRE_PDFIUM=1 cargo test --workspace`, 0 failures).

Grep of non-test code in the crate for `unwrap()`, `expect(`, `panic!`, `unreachable!`: none. Narrowing casts: `layout.rs:93` `(s*2.0).round() as i32` (saturating float->int cast, sizes are pre-filtered by `finite()`), `layout.rs:575` — the **F31 defect**. Geometry hardening already present: `finite()` (`abs < 1e7`) rejects NaN/inf/huge glyph coordinates (`glyphs_to_frags`), `band_of`/`find_gutters` guard non-finite/non-positive page size, bin counts capped (`min(4000)`), slice ranges `a..=b` proven in-bounds because x1 >= x0 per fragment. I tried to break these and found no panic path.

**F31 (found, proven, fixed).** `level_of` computed `((rank + 1) as u8).min(MAX_HEADING_LEVEL)`: the 256th-largest distinct heading size wraps to 0, yielding `Block::Heading{level:0}` and a `Section.heading` of level 0 (which the `lvl <= 2` rule treats as a section start). Proof: new test `layout::tests::many_distinct_heading_sizes_never_yield_level_zero` (320 pages, one heading each, sizes 14.0 + 0.5*i) panicked with `level 0` on the unfixed code (I temporarily restored it with `sed` to confirm) and passes with `(rank + 1).min(MAX_HEADING_LEVEL as usize) as u8`. Impact is cosmetic (TOC/heading style) — no memory-safety effect — but it is hostile-input-controlled output.

**F36 (not fixed).** Memory/CPU shape: see the table row. Not exercised with a stress PDF; reasoned from `extract()` and `page_to_lines`.

## 5. FFI, tables, Swift renderer (checklist 3-5)

**FFI (checklist 3).** `git diff 0293fee..HEAD -- crates/gist-ffi` adds zero `#[uniffi::export]` lines; it adds three `GistError` variants (`PdfEncrypted`, `PdfNoTextLayer`, `PdfUnavailable`) and the `From<ImportError>` arms. The crate has 6 `uniffi::export` blocks and 44 `ffi_catch!` uses; the only export that reaches the PDF parser is the pre-existing, `ffi_catch!`-wrapped `import_file`. `PdfUnavailable(_)` drops its detail; `ImportError::Pdf(String)` falls to `GistError::Core(to_string())`, built from a fixed phrase or the Debug of pdfium's error enum — no paths, no panic payloads. `set_library_path` is not exported.

**Tables / IR v2 (checklist 4).** `required_ir_version` (`gist-store/src/lib.rs:322-333`) stamps a document blob v2 only if it holds a `Block::Table`; tokens blobs are always `IR_VERSION_BASE` (`:1002`); document blobs use `required_ir_version(doc)` (`:991`). Tests at `:4419-4500` play an old binary via `deserialize_ir_blob_with_max(.., IR_VERSION_BASE)` against a local `pre_table::Document`: a v1-stamped table blob fails with `unknown variant Table` (evidence for the bump), the real v2 blob yields typed `IrVersionTooNew`, and a table-free doc is v1 and readable by an old binary. All pass in the workspace run. Other consumers: FTS indexes the token stream (tables linearised per row, `gist-model/src/lib.rs:336`); annotation reanchoring uses `section_text` with the tab/newline golden pinned in `gist-core` (`section_text_with_a_table_matches_the_cross_language_golden`) and mirrored by a Swift test; the Windows app only passes `GetDocumentJsonAsync` through as a string (`apps/windows/GIST.Core/Client/CoreClient.cs:806`) and has no C# `Block` model. Table limits are checked before the push in DOCX (`gist-parse-docx/src/lib.rs:448`, `:664`), ePub (`gist-parse-epub/src/lib.rs:356`, `:598`) and web (`gist-web/src/lib.rs:557`, `:570`).

**Swift renderer (checklist 5).** `PdfPageRenderer.swift`: temp root is `FileManager.default.temporaryDirectory` (the per-app container tmp in the sandbox, not a shared location) plus `gist-pdf-ocr-<UUID>`; files written `.atomic`; the directory is removed on every thrown path and by `OcrImportModel.cleanupPdfTemp` on every terminal phase. Caps: page cap before the directory exists; 200 DPI; 4096 px/side; per-page `OcrFileSizeCheck.maxBytes` with one low-quality retry; 2 GiB total. `maxPages = 2_000` equals `ParseLimits::default().max_pages` today (`gist-model/src/lib.rs:40`). Security-scoped access is re-acquired in `beginPdf` and released on every exit. Findings: F32 (fixed), F35 (open). PDFKit's own crash surface is out of scope.

## 7. Fuzzing (checklist 7)

Built with `cd fuzz && cargo +nightly fuzz build fuzz_parse_pdf` (clean). Harness panics if pdfium is not loadable, and it was (debug-assertions build finds `artifacts/pdfium/lib`). Runs (libFuzzer "Done N runs"), all with zero crashes, no `crash-*`/`oom-*`/`timeout-*` artifacts:

| Target | Requested | Runs | Wall-clock |
|---|---|---|---|
| fuzz_parse_pdf (`-max_len=1048576 -timeout=20`) | 300 s | 33,715 | 588 s |
| fuzz_parse_txt | 60 s | 457,100 | 87 s |
| fuzz_parse_epub | 60 s | 204,876 | 345 s |
| fuzz_parse_docx | 60 s | 352,272 | 1022 s |
| fuzz_web_extract | 60 s | 737,891 | 61 s |

**The "slowest unit" anomaly is host stalls, not real hangs.** Wall-clock far exceeded the requested time for pdf/epub/docx/txt, and libFuzzer wrote `slow-unit-*` artifacts for docx, epub and txt. I re-executed each saved slow unit directly (`fuzz_parse_<t> artifacts/fuzz_parse_<t>/slow-unit-*`): all three completed instantly (the txt one is 492 bytes), and the PDF run had `-timeout=20` and produced no timeout artifact. The stalls coincided with my other cargo/xcodebuild jobs and with the session being suspended; I could not prove the cause beyond that. I deleted the generated corpus and artifacts (`git clean`), committing only the existing seeds. PDF exec throughput (~57/s) is low, as expected for a C++ parser via FFI; coverage is therefore much shallower than for the pure-Rust targets and a clean result is weak evidence.
