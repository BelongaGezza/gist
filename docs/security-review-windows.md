# Windows shell security review (F27)

**Date:** 2026-10-04 · **Tree:** `integration/w4-2026-10-04` @ `94a164c` (W4 R1 and R3 merged; W4 R2, the RSVP reader view, is **not** in this tree and is **not** reviewed)
**Reviewer role:** W4 role R4, an independent reviewer who wrote none of this code. Source was read-only. The only write is this report.
**Follow-up to:** `docs/review-pre-w1-quality-security.md` (2026-09-20), the last Windows review. Register row `F27` asks for this pass.

## 1. Summary

No High or Medium defects found. Seven Low and three Informational items are recorded below.

| ID | Severity | Where | One line |
|---|---|---|---|
| F39 | Low | `gist-core` sweep, `gist-store::insert_item` | Orphan sweep has no age grace and nothing stops it overlapping an import in a second GIST process |
| F40 | Low | `gist-core::remove_items_detailed` | The DB-sourced blob paths are deleted without the `is_inside` guard that the stored copy gets |
| F41 | Low | `CoreClient.MapGistException`, `CoreError` | Raw Rust message text is stored in `CoreError.Message` (documented as never carrying a path), and `ChecksumMismatch` collapses to a generic kind |

## 4. Findings

### F39: Orphan sweep can delete a just-written import. **Low** (reading-only)

- **Evidence:**
  - `Store::insert_item` writes `<id>.json` and `<id>.tokens.json` (plus sidecars) to the storage directory first (`crates/gist-store/src/lib.rs:996-1008`). It then opens the DB transaction that inserts the row and all FTS token rows (`:1024` onward). `store_original_copy` also runs before the row exists.
  - `Core::sweep_orphaned_files` (`crates/gist-core/src/lib.rs:1336`) takes a snapshot of referenced files, then deletes every pattern-matching file that is not in the snapshot. `sweep_dir` (`:305`) has no modification-time grace.
  - Within one process, `CoreClient` serialises sweep, import and removal through `_ffiGate` (`CoreClient.cs:48`, `InvokeAsync`), so there is no overlap there.
  - The sweep runs at every app start (`StartBackgroundSweep`).
  - Nothing enforces a single GIST instance: I found no `AppInstance`, named mutex or equivalent in `apps/windows/GIST.App`.
  - The Rust `Core` and `GistCore` take `&self` with no cross-call lock, so any second caller on the same storage directory has no protection.
- **Reasoning:** a second GIST process started while the first is importing a large document (the FTS insert can take seconds) runs its startup sweep inside that window. It deletes the new blobs and the stored original copy.
  - The row is then committed pointing at missing files. The item shows in the library and cannot be opened.
  - Without the copy, `ChecksumMismatch` is not even the symptom; the read simply fails.
  - The user's real file is untouched (ADR-006), so the fix for the user is a re-import. That is why this is Low.
- **Not reproduced.** It needs two processes and precise timing, but the ordering is plain in the code.
- **Recommended fix:**
  - (a) Skip any candidate whose mtime is newer than a grace period (a few minutes).
  - (b) Enforce single instance with `AppInstance.FindOrRegisterForKey` or a named mutex around the store.
  - (c) Make the sweep skip files while an import is in flight in the same process. This is already true via `_ffiGate`; document the cross-process gap.
  - Option (a) is the cheapest and covers non-`CoreClient` callers too.

### F40: Removal deletes DB-sourced blob paths without the containment check. **Low** (reading-only)

- **Evidence:** the `remove_items_detailed` doc says `is_inside` exists because "removal is the one place that deletes a path read back out of the database" (`crates/gist-core/src/lib.rs:203-225`). The guard is applied only to `source_copy_path` (`:1256`). `item.doc_path`, its `.tokens.json` sibling and their `.blake3` sidecars go straight to `tally.try_delete_with_sidecar` (`:1248-1249`). `doc_path` is also a column read back from the DB.
- **Reasoning:** a tampered or corrupted `library_items.doc_path` can make removal delete an arbitrary user-writable file. It also deletes `<that path>.tokens.json` and `<that path>.blake3` if they exist.
  - Exploiting it requires write access to the user's SQLite file, which is the same trust level as deleting those files directly. Hence Low.
  - The code's own stated rationale is applied inconsistently, so it is worth closing. This is shared Rust, so Apple is affected identically.
- **Recommended fix:** apply `is_inside(storage_dir, …)` to `doc_path` and the derived tokens path exactly as is done for the stored copy, with the same refuse-and-`debug!` behaviour. Add a test with a row whose `doc_path` points outside storage.

### F41: Raw core text in `CoreError.Message`; integrity errors lose their kind. **Low** (confirmed by reading and grep)

- **Evidence:**
  - `MapGistException`'s fallthrough arm is `_ => new CoreError(CoreErrorKind.Core, e.Message)` (`CoreClient.cs:931`).
  - `e.Message` is the Rust `Display` text: `io: …`, `store: …`, `parse: …`, `item not found: <id>`, and `checksum mismatch for <absolute internal storage path>: …` (`crates/gist-store/src/lib.rs:46`).
  - The `CoreError` doc claims "the messages produced here never embed a file path or a document title, so it is safe to show anywhere" (`CoreError.cs`). That is false for this arm.
  - It is currently harmless because the product UI never displays `Message`. `DialogContent.ErrorMessage(kind)` chooses fixed text from the kind alone (`DialogContent.cs`), and a grep of `apps/windows/GIST.App` and `ViewModels` finds no other consumer.
  - `GistException.ChecksumMismatch`, `PdfEncrypted`, `PdfNoTextLayer` and `PdfUnavailable` have no `CoreErrorKind`. They all become `Core` and then the generic "That action couldn't be completed."
  - Nothing in `apps/windows` calls `VerifyItemIntegrity` or `VerifyLibraryIntegrity`.
  - `EncryptItemsSummary.ScrubFailure` classifies failures by string prefix of the raw error text. That contradicts the stated "match by type, never message text" rule, though its fallback is safe and generic.
- **Impact:**
  - Latent leak: any future caller that shows or logs `LastError.Message` would expose internal paths, which include the user's profile name, and item ids.
  - Functional and security-adjacent: ADR-013 and register row `A4` require an on-disk integrity failure to be presented distinctly ("never a generic error"). Windows currently cannot do that.
  - PDFs are not offered by the Windows picker (`ImportFilePicker`: `.txt`, `.epub`, `.docx`), so the Pdf* arms are not reachable today.
- **Recommended fix:**
  - Add `CoreErrorKind.ChecksumMismatch` (and the Pdf kinds when PDF is enabled), matched on exception type like DRM.
  - Make the `Core` arm use a fixed message and keep the raw text out of the model.
  - Keep `ScrubFailure` as a fallback only.
  - Wire the integrity verifier into the Windows Settings/Storage surface when that lands (plan W6).

### F42: Dev/test environment overrides are live in release builds. **Low** (confirmed by reading)

- **Evidence:**
  - `AppServices.Initialize` reads `GIST_DATA_ROOT` unconditionally (`AppServices.cs:44`). When set, it redirects the database, storage and key directories to that root and enables `WriteDiagnostic`, which appends `diag.log` there. The comment says "Never set by the product", but nothing enforces it.
  - `DialogHarness.RunIfRequested` is likewise always compiled and runs when both variables are set.
  - Contrast the Apple shell, where dev-only fallbacks are compiled out of release (`cfg(debug_assertions)`, M6 R7).
- **Reasoning:** an actor who can set the environment of the GIST process already acts as that user, so this is not an escalation. It is an unnecessary way to point a release build at an attacker-prepared store and key directory. A prepared key file would be read as the real key.
  - It also makes the "release build has no test seams" claim false.
- **Recommended fix:** gate both behind `#if DEBUG` or an explicit MSBuild constant that the UI-test and verify scripts build with.

### F43: Unchecked `elapsed_at_pause +=` on a client-supplied `u64`. **Low** (reproduced)

- **Evidence:** `RsvpSession::pause` does `self.elapsed_at_pause += elapsed_ms;` (`crates/gist-rsvp/src/lib.rs:404`). `FfiRsvpSession::pause` passes the C# `u64` straight through (`gist-ffi/src/lib.rs:951`).
- **Reproduced:** two `pause(u64::MAX)` calls with a resume between.
  - Debug profile: `panicked … attempt to add with overflow`. Under `ffi_catch!` this surfaces as `InternalPanic`, after the cursor has already been mutated on the previous line. The session is left half-updated.
  - Release profile (overflow checks off): silent wrap, `elapsed_at_pause = 18446744073709551614`, so every later `stats_at_elapsed` duration is nonsense.
- **Impact:** a real caller measures elapsed with a `Stopwatch`, which cannot reach this range. The risk is the API contract: the doc and the FFI header say nothing here can panic on client input. `stats_at_elapsed` already uses `saturating_add`, so `pause` is the inconsistent one. `token_at_elapsed_naive` also has an unchecked `accumulated + dur`, but it is only a test reference and a defensive fallback.
- **Recommended fix:** `saturating_add` in `pause`, plus a regression test with `u64::MAX`.

### F44: One very long token makes every reader tick expensive. **Low** (reproduced, UI impact not assessed)

- **Evidence:**
  - Tokenisation is `split_whitespace` with no length cap (`gist-model/src/lib.rs:369`), and the txt parser allows files up to `max_bytes` (256 MiB).
  - `FfiRsvpSession::frame_at_elapsed` returns `text`, plus an `FfiOrpSplit` that copies the text three more times. It also runs `orp_split`, which builds a `Vec` of every grapheme cluster, on each call (`gist-ffi/src/lib.rs:907-934`, `gist-rsvp/src/lib.rs:533+`).
- **Measured:** a single 20,000,000-character token took 420 ms (release) and 2.9 s (debug) for one `orp_split`. `token_duration_ms` was 10-15 µs, so the cost is the ORP and clone path, not pacing.
- **Impact:** a hostile or malformed document with a huge unbroken run opens fine, then the reader stalls or spikes memory on every tick, and the marshalled strings are copied into managed memory each time. Local self-DoS only. How much this matters depends on R2's tick loop, which I did not review.
- **Recommended fix:** split over-long tokens during tokenisation (for example at a few hundred characters), or bound the ORP window. At minimum, do not return `text` and three copies per frame.

### F45: The Windows build and its gates are not required checks. **Low** (confirmed)

- **Evidence:**
  - `windows-build.yml` carries a header comment saying it must not be a required check, because it is paths-filtered.
  - `gh api …/branches/main/protection` shows required contexts `quality` and `test (ubuntu-latest|macos-latest|windows-latest)` only.
  - So the following can fail on a PR touching only `apps/windows/**` and still be merged: bindings reproducibility, the bindgen `exclude` guard, locked-mode restore, the NuGet High/Critical vulnerability gate, `dotnet build`/`test`, and the ARM64 cross-compile.
  - The 2026-09-20 review (Q4) recommended adding `windows-build` to required checks once it existed.
- **Mitigating:** the Rust core's Windows leg (`test (windows-latest)`) is required and runs the release panic probe and the DLL-imports check. The workflow itself is sound: pinned SHAs, `permissions: contents: read`, `pull_request` rather than `pull_request_target`, and a pinned mirror generator rev.
- **Recommended fix:** remove the path filter and make the job cheap-exit when nothing relevant changed, or add an always-running `windows-gate` job that depends on it, and require that. Add `CODEOWNERS` review if single-maintainer constraints allow.

### F46: Package capabilities. **Informational** (reading-only; no package has been installed)

- `Package.appxmanifest` declares `internetClient` and `rescap:runFullTrust` only, with no `broadFileSystemAccess` and no `privateNetwork*`. The comment correctly says files come via the picker. That is the minimum for this design.
- Under `runFullTrust` there is no AppContainer, so `internetClient` constrains nothing at runtime. The only network defence is `gist-web`'s TLS-only, SSRF-safe resolver and redirect rules (`F14`). The same applies to file access: the process has the user's full file rights, so the "never touches user originals" rule rests on ADR-006 and the removal code, not on the OS.
- ADR-017 already states full-trust MSIX is weaker than the macOS sandbox. This item exists so nobody reads the capability list as a sandbox.
- `Publisher="CN=GIST Dev"` is a placeholder, and the manifest has never been built into an installed package. Both are tracked under W6.

### F47: Key-custody residuals. **Informational** (reading-only)

- The DPAPI entropy default `GIST.KeyProvider.v1` is a public constant, so any same-user process can unwrap the key blob. ADR-016 accepts this, and DPAPI plus the ACL is not a sandbox.
- `KeyStoreAcl` returns "hardened" when the directory is already ACL-protected, without inspecting the existing rules (`KeyStoreAcl.cs:32`). A pre-existing protected ACL that grants others access would be trusted as is.
- Removing inherited rules also removes SYSTEM and Administrators. That is deliberate, but an SYSTEM-run backup or AV agent can no longer read the key directory.
- Key bytes live in managed memory for the process lifetime (`CoreClient._key`, `PreObtainedKeyProvider`). `Dispose` nulls them without `ZeroMemory`. ADR-016 accepts non-zeroing; the effect is a slightly longer exposure window in process dumps.
- `ReadKeyFileBytes` reads the whole file with no size bound; the directory is user-owned, so this is not exploitable.

### F48: Native library trust. **Informational** (reading-only)

- The loader behaves as documented: assembly-level `DefaultDllImportSearchPaths(AssemblyDirectory)`, plus a `ModuleInitializer` resolver that loads `gist_ffi.dll` by absolute path from the assembly directory, then `runtimes/win-{x64|arm64}/native/`, else falls through to the restricted default. It never uses PATH or the current directory.
- That makes location the only trust. There is no hash, Authenticode or version-contract check of the DLL beyond uniffi's own contract-version and per-function checksum verification at load time. In an unpackaged build the output directory is user-writable. Once MSIX-packaged, the package contents are signed and read-only, so this concern applies to unpackaged/dev builds only.
- Not a defect. A signed-release launch check (the `N8` pattern) should include loading the packaged DLL.

## 5. Checked and found sound

- **FFI exports and `ffi_catch!`:** every exported `pub fn` in `crates/gist-ffi/src/lib.rs` (a grep listing each export beside its `ffi_catch!`), including every `FfiRsvpSession` method, `rsvp_orp_split` and `open_rsvp_session`, was checked. Each body is wrapped in `ffi_catch!`. The panic hook only routes to `tracing::debug!` (F22). The release profile is `panic = "unwind"`, and the release panic-containment probe passed on this tree.
- **Lock poisoning:** `FfiRsvpSession::lock` is `unwrap_or_else(|p| p.into_inner())`. There is no bare `.lock().unwrap()` in the new code (grep of `crates/gist-ffi`).
- **Index and cast safety:** indices from C# go through the saturating `ffi_index`/`ffi_u64`. All out-of-range reads use `Option` or clamp, and `back_words`, `seek` and an empty token stream are covered by tests and by reading. `open_rsvp_session` clamps WPM and returns a typed error for an unknown id.
- **Schedule memoisation:** bounded by token count (one `u64` per token). The key covers config, token count and cursor, and the memo is proven equal to the naive scan by the exhaustive test.
- **Key custody:**
  - The key is fetched eagerly in managed code, validated to 32 bytes, and handed to Rust through a provider that cannot throw. A corrupt key file parks the client in a blocking state and nothing is regenerated, deleted or rewritten.
  - Create is atomic (temp file, then `File.Move` without overwrite) and race-safe. Transient DPAPI failures are classed retryable, and only `ERROR_INVALID_DATA`/`ERROR_INVALID_PARAMETER` count as proven corruption.
  - The key directory is hardened to the current user alone, inheritable, and the key file inherits it; `DpapiKeyProviderTests` assert both. Stale temp files are reaped only if they match the strict name pattern and are over a minute old.
  - Key, database and storage directories all derive from one `GistStoragePaths` root.
- **Removal and encrypt semantics:**
  - Windows always passes `deleteSourceFiles: true`, which deletes only the sandboxed ADR-006 copy, guarded by `is_inside` (canonicalised, reparse-point-safe) and by shared-copy reference tracking. The user's real `source_path` is never used for deletion.
  - The sweep deletes only names that match generated UUID/SHA-256 patterns, in the storage directory and `originals/`, non-recursively. It skips symlinks and junctions at both directory and file level, matches names case-insensitively on the keep side, and never touches `keys/` (a sibling directory) or the SQLite files.
  - `EncryptItemsAsync` reuses the client's own key, and the `NewWithReadKey` pattern means encrypted items stay readable.
- **Logging policy:** `CoreClient` and the Windows shell emit no log records. Source paths appear only in `debug!` in Rust. The `diag.log` writer records counts and state names only.
- **Native loading:** no `PATH` or current-directory lookup (F48 caveat above). The only other P/Invoke is `kernel32!GetCurrentPackageFamilyName`, which is a known system DLL. The static-CRT build was verified: release DLL imports no VC++ runtime.
- **Supply chain:** NuGet versions are exact in central package management, with lock files committed, locked-mode restore in CI, and `NuGetAudit` at High. The bindgen is pinned by full rev on a project-controlled mirror, with the install-record check and the `exclude` guard. All Windows workflow actions are SHA-pinned and `permissions: contents: read`. `CODEOWNERS` covers `apps/windows`, `tools`, `.github` and the PENDING handoff files.
- **File picker and paths:** the picker is initialised with the window handle and filtered to `.txt/.epub/.docx`. An empty or null result is handled. `long path aware` is on in `app.manifest`. Import paths come only from the picker, and `ImportFileAsync` checks existence in managed code first.
- **Exception boundary:** `GistException` and the generated types are `internal` to `GIST.Core`, so they are not part of any public API. `InvokeAsync` converts every managed exception to a typed `CoreError`, and InternalPanic text is discarded.

## 6. Recommended order

1. F40 (small, shared Rust), F43 (one line plus a test) and F41 (kind mapping), as they are cheap and reduce latent risk.
2. F39 (age grace on the sweep and/or single instance) before more writers appear, such as W4/W5 progress saving and OCR on Windows.
3. F42 (`#if DEBUG`) before any packaged build is distributed.
4. F45 (required Windows gate) before W4 merges to `main`.
5. F44 when the reader tick loop (R2) is reviewed.
