# ADR 013 — At-rest integrity checksums

**Date:** 2026-09-18
**Status:** Accepted, Rust-side implemented and tested; no production/Swift wiring in this pass

## Context

Security register item `A4` (open since Security Review v1, 2026-09-08, milestone-gated to M4) flagged that GIST has no way to detect silent on-disk corruption of the content it persists: ADR-007's IR blobs (`<id>.json`/`<id>.tokens.json`) and ADR-006's copy-on-import originals (`originals/<hash>.<ext>`) are written via plain `std::fs::write` (or, since ADR-011, `encrypt_at_rest`'s AES-256-GCM output) and later read back with no check that the bytes on disk still match what was written. Bit rot, a failing disk, a partial write interrupted by a crash, or a user's backup/sync tool doing something unexpected could all silently hand corrupted bytes to `serde_json::from_slice` (for IR blobs) or leave a corrupted original copy nobody ever notices. This is orthogonal to ADR-011 (`A6`, encryption-at-rest, confidentiality): a checksum says "this file is unchanged since it was written," it says nothing about whether an attacker without the key could read it.

`A4` originally named BLAKE3 as the likely algorithm without deciding the scope, write/verify points, schema impact, or corrupted-data behavior. This ADR makes those decisions and records the same "decide + implement + test the Rust side now, leave Swift/production wiring as an explicit follow-up" pattern ADR-011 (`A6`) used ahead of its own M4 gate.

## Decision

**What gets checksummed:** every file `gist-store` writes as document content — `<id>.json`, `<id>.tokens.json` (ADR-007), and each `originals/<hash>.<ext>` copy-on-import file (ADR-006). Nothing else (the SQLite database itself has its own well-established integrity mechanisms via WAL/journaling, and is out of scope here).

**Algorithm: BLAKE3**, via the `blake3` crate. Confirmed compatible with `deny.toml`'s license allow-list with **no change to that file**: `cargo metadata` reports blake3 1.8.7's license as `CC0-1.0 OR Apache-2.0 OR Apache-2.0 WITH LLVM-exception`; both `Apache-2.0` and `Apache-2.0 WITH LLVM-exception` are already on the allow-list (added for uniffi/scraper), and cargo-deny accepts an SPDX `OR` expression once any one of its arms is allowed. `cargo deny check licenses` (and `bans`/`sources`) were re-run after adding the dependency and are genuinely green — see Verification. BLAKE3 is a fast, non-cryptographic-integrity-appropriate hash (this is corruption detection, not a security boundary — the app has no untrusted party feeding it document bytes it needs to authenticate, only its own prior writes to itself), and its crate has no C toolchain/build-script dependency to complicate the existing `cargo-fuzz`/xcframework build story.

**Mechanism: a checksum sidecar file, not a new `library_items` column.** For a checksummed file at `<path>`, a plain-text sidecar `<path>.blake3` is written alongside it, containing just the 64-hex-character digest. This was chosen over a schema column (the ADR-011/schema-v4/v5 precedent for `content_encrypted`/`source_copy_path`) for three reasons:

1. **Uniform across all three file kinds.** `originals/` copies are content-addressed and can be referenced by more than one `library_items` row (ADR-006's documented dedup limitation) — a per-item DB column doesn't have an obvious single owner for a shared file's checksum, whereas a sidecar keyed by the same path the content file already uses has one unambiguous owner: the file itself.
2. **Nothing here is ever queried or filtered in SQL.** Unlike `content_encrypted` (which `get_item`/`get_tokens` branch on per-row) or `source_copy_path` (which removal logic reads), a checksum is only ever compared against the one file it names, at the moment that file is read. There's no case for `WHERE`-clauseing over checksums, so there's no relational-modeling reason to put them in SQLite.
3. **Fits ADR-007's existing ethos.** ADR-007 chose JSON-on-disk specifically so "contributors can open any `<id>.json` or `<id>.tokens.json` directly to inspect a parse result" — a plain-text sidecar with a 64-character hex digest is exactly as inspectable, and needs no SQLite client to read.

**Consequence:** no schema migration, no `SCHEMA_VERSION` bump. This is a deliberate, load-bearing part of the decision, not an oversight — see Consequences for the one thing it costs.

**When computed:** on every write of a checksummed file's content —
- `Store::insert_item` writes `<id>.json` and `<id>.tokens.json`'s sidecars right after each blob is written (over the *exact bytes written to disk* — see the encryption interaction below).
- `Store::store_original_copy` writes a sidecar right after a *fresh* copy is written. A dedup hit (identical content already exists at the content-addressed path, per ADR-006) leaves the existing file **and its sidecar** untouched, exactly mirroring the existing "never rewrite an existing file" contract for the content itself — see Backfill below for what this means for a copy that predates this feature.

**When verified — automatically for IR blobs, on read, not yet wired for originals:** `Store`'s single shared `read_maybe_encrypted` helper (used by both `get_item` and `get_tokens`) now verifies the sidecar, if one exists, immediately after reading raw bytes from disk and *before* attempting decryption. This means every real read path for document content in the app goes through checksum verification automatically, with no call-site changes needed anywhere above `gist-store`.

For `originals/` copies, there is — as ADR-006 already documents — no existing call site in the app that reads an original copy's *content* at all (removal only reads the DB row's *path* to delete it; nothing decodes the bytes). So there is no "on read" moment to hook into automatically today. `Store::verify_original_copy(path)` is provided as the primitive a future maintenance action ("verify library integrity") would call, implemented and tested now, but not wired to anything — the same "implemented, dormant, no live caller" pattern this codebase already uses for `N4`/`A7`.

**On mismatch: a typed, hard error — never silent pass-through.** A new `StoreError::ChecksumMismatch { path }` variant is returned by `read_maybe_encrypted` (and thus surfaces through `get_item`/`get_tokens`) and by `verify_original_copy`. This was a deliberate call, not an assumed default:

- GIST is a personal, single-user reading app; every checksummed file was written by this same app, to its own sandboxed storage. A mismatch here is not an adversarial-input problem needing graceful degradation for an untrusted third party — it means *this specific file, on this specific disk, is no longer what GIST wrote*.
- Continuing past a mismatch (e.g. attempting to deserialize a corrupted `<id>.json` anyway) risks a confusing downstream panic or, worse, a corrupted-but-still-parseable document silently mis-rendering to the reader — strictly worse than a clear, typed failure the UI can present as "this item appears damaged."
- Corruption is what checksums exist to detect in the first place; treating a positive detection as informational-only (e.g. a log line, content served anyway) would make the whole feature nearly pointless for a single-user app with no server-side redundancy to fall back to.
- This mirrors `DecryptionFailed`'s existing precedent in the same file: both are "the bytes on disk are not what they should be" failures, and both fail loudly rather than guessing.

**Interaction with encryption (ADR-011):** the checksum is computed over the bytes actually written to disk — ciphertext when the `Store` is encrypted, plaintext otherwise — not over the pre-encryption plaintext. Verification therefore runs *before* decryption is attempted, so a corrupted encrypted file is reported as `ChecksumMismatch`, not conflated with `DecryptionFailed` (which by design gives no detail on *why* decryption failed, since AEAD implementations deliberately avoid distinguishing failure reasons). This does mean AES-GCM's own authentication tag is, for encrypted content, a second, redundant integrity check — accepted deliberately: it keeps the checksum mechanism identical and independently testable regardless of encryption status, and costs nothing (BLAKE3 is fast enough that hashing a full ciphertext blob before an AEAD decrypt of the same blob is not a meaningful overhead at this app's document sizes).

## Backfill: existing files have no checksum

Every file written before this feature existed — anything currently on a user's disk — has no `.blake3` sidecar. `verify_checksum`'s policy: **a missing sidecar is not an error.** It's treated as "unverified," not "verified and passing," and not "corrupt." No claim of integrity is made about it either way; the file is simply read (and, if applicable, decrypted) exactly as it always was. Only a sidecar that *exists but disagrees* with the file's current content triggers `ChecksumMismatch`.

This is the same shape of decision ADR-011 made for its own migration story (a per-row flag defaulting to "not encrypted" for pre-existing rows, no bulk rewrite) applied to a simpler mechanism that doesn't need a DB flag at all — file presence/absence of the sidecar *is* the flag. No eager backfill pass (re-reading every existing file to write a sidecar for it at first touch) was implemented, for the same reasons ADR-011 rejected eager bulk re-encryption: this app's document content is otherwise immutable after import, there's no existing "rewrite this file" code path to piggyback on, and a partial backfill interrupted mid-way is a worse failure mode to reason about than "old files simply stay unverified until they're naturally re-imported."

**Consequence to track:** without a future explicit backfill/maintenance action (not built here), a file present before this lands never gets a checksum unless the item is removed and re-imported. This is accepted, not an oversight — flagged here exactly as ADR-011 flags its own equivalent gap.

## What was implemented

- `gist-store`: `blake3` dependency (workspace-declared in the root `Cargo.toml`, same pattern as `sha2`); `StoreError::ChecksumMismatch { path: String }`; `checksum_hex`/`checksum_sidecar_path`/`write_checksum_sidecar`/`verify_checksum` helpers; `Store::insert_item` writes a sidecar for both the document and tokens blobs; `Store::store_original_copy` writes one for a freshly-written original copy; `Store::read_maybe_encrypted` (shared by `get_item`/`get_tokens`) verifies before decrypting; new public `Store::verify_original_copy(path)` for the not-yet-wired originals case described above.
- `gist-core`: `Core::remove_items`'s existing best-effort file-cleanup loop now also deletes each blob's `.blake3` sidecar alongside it (`remove_file_and_checksum_sidecar`, replacing three near-identical inline `std::fs::remove_file` call sites), so removing an item doesn't leave an orphaned checksum sidecar behind. Same best-effort/`debug!`-logged-on-failure policy as the existing file deletions.
- No `gist-model` changes were needed — this is entirely a `gist-store` file-boundary concern, unlike ADR-011's `KeyProvider` trait, which needed to be visible at the `gist-core` facade layer because callers construct it. Nothing above `gist-store` needs to know checksums exist at all.
- Test coverage (`gist-store`, 12 new tests): a round trip confirming `insert_item` writes sidecars whose recorded digest matches the actual on-disk bytes and that normal reads still succeed; deliberate-corruption tests for both the document blob and the tokens blob (flip a byte on disk, assert `Err(ChecksumMismatch)`); a legacy/backfill test (delete the sidecars after a normal insert, assert reads still succeed); a `store_original_copy` write+`verify_original_copy` round trip; a corrupted-original-copy test; a missing-sidecar-is-not-an-error test for `verify_original_copy`; a dedup-hit test locking in that re-importing identical bytes does not backfill a sidecar deliberately left missing; and an encrypted-store test confirming a corrupted ciphertext blob is reported as `ChecksumMismatch` (checked before decryption is attempted), not `DecryptionFailed`. Two existing `gist-core` tests (`remove_items_with_delete_source_files_{true,false}...`) were updated: their `the_one_sandboxed_copy` helper now filters out `.blake3` sidecar files when asserting "exactly one copy exists" in `originals/`, and the `true` case gained an assertion that the sidecar is cleaned up alongside its copy.

## What was not implemented (this pass)

- **Any Swift/Apple-side change.** No new FFI surface, no `apps/apple/` change, no UI for "this item is corrupted." A `ChecksumMismatch` reaching `gist-ffi` today just becomes an opaque `GistError` like any other `StoreError` variant — there is no dedicated, typed presentation for it the way `GistError::DrmProtected` gets one. That's a real gap for a good user experience (a corrupted item should probably say so, not just fail to open with a generic error), left for whoever wires this up to decide, consistent with this being a Rust-side-only pass.
- **A backfill/maintenance action** that could compute sidecars for a user's already-imported library, or a "verify library integrity" UI feature that would call `Store::verify_original_copy` for every `originals/` file. Both are natural follow-ups once there's a UI layer to surface results in.
- **Any encryption/`KeyProvider`/AES-GCM change.** This ADR does not touch ADR-011 or its `A6` register row in any way — orthogonal work, left alone, as directed.

## Verification

`cargo test --workspace`, `cargo clippy --workspace -- -D warnings`, `cargo fmt --check`, and `cargo deny check bans licenses sources` were all actually re-run in this session against the finished change and are genuinely green: `gist-store` now has 47 passing tests (35 pre-existing + 12 new), `gist-core` has 13 (including the two updated removal tests), and the full workspace suite passes with zero failures. `cargo deny check licenses` (and the combined `bans licenses sources` gate) was specifically re-checked after adding `blake3` and needed no allow-list change, confirming the licensing analysis above against the actual resolved dependency, not just its crates.io listing. No Xcode/Swift build was run for this pass, since nothing in `apps/apple/` changed.

## Consequences

**Easier:** a future "why does this book look wrong" support/debugging question now has a first stop — check whether the item's blobs still pass their checksum — instead of only being able to shrug at a parse error. Any future feature that writes new file-boundary content in `gist-store` can reuse `write_checksum_sidecar`/`verify_checksum` directly.

**Harder / to watch:** a corrupted item now hard-fails to load rather than potentially still rendering something (garbled but partially readable) the way un-checksummed corruption sometimes silently would have — this is the deliberate tradeoff described above, but it does mean any real-world corruption (rare, but not impossible on consumer hardware over years) turns into a harder failure than before this ADR, for exactly the class of file that was already the most likely to matter to the user (their books). No repair mechanism exists — a truly corrupted item's only recovery path today is re-importing it (if `source_path`, the original file, is still reachable) or discarding it; a "your progress/annotations on that copy are gone" gap that a future repair/re-checksum feature would need to address, not evaluated further here. Because there's no schema flag for "this row's checksums are missing," there's also no SQL-level way to ask "how many of my items are still unverified (pre-this-feature)" without walking the filesystem directly — a query a bulk-backfill feature would need to build itself, since this ADR didn't add one.
