# ADR 017 — Windows packaging, identity and sandbox: MSIX, with an unpackaged dev loop

**Date:** 2026-09-20
**Status:** Proposed (distribution channel deliberately undecided until W6)

## Context
ADR-012 gives the macOS app an App Sandbox: user-selected file read/write and outbound network only. `docs/windows-development-plan.md` §3 proposed MSIX for Windows as the analogue. This ADR fixes the packaging model and records what was actually verified on the Windows dev machine on 2026-09-20 (Windows 11 Home 10.0.26200, .NET SDK 10.0.401).

Verified facts (run, not recalled):
- Installed Visual Studio: Community 2026 (18.10) with only the **Native Desktop (C++)** workload; Build Tools 2022 (17.14) with native-desktop core components. No WinUI / Windows App SDK C# / MSIX-packaging / .NET desktop workload is installed. Windows SDK 10.0.26100.0 is present (`makeappx.exe`, `makepri.exe`, `signtool.exe` exist under its `bin\...\x64`). No .NET workloads installed.
- A WinUI 3 app created **by hand, without VS templates** (`apps/windows/spikes/winui-hello`, `net10.0-windows10.0.19041.0`, `Microsoft.WindowsAppSDK` 2.5.1 from nuget.org, `UseWinUI`, `WindowsPackageType=None`, x64) restored and built with plain `dotnet build` (0 warnings, 0 errors). Launched, it stayed alive for the 6 s check, showed its window title, and loaded `gist_ffi.dll` (built with `cargo build -p gist-ffi`) from beside the exe via `NativeLibrary.TryLoad`.
- The same project with `WindowsPackageType=MSIX`, a hand-written `Package.appxmanifest`, `EnableMsixTooling=true`, `GenerateAppxPackageOnBuild=true`, signing disabled, produced `winui-hello_0.0.1.0_x64_Debug.msix` plus Windows App Runtime dependency MSIXs, still with plain `dotnet build` and no VS workload. One warning: `mspdbcmf.exe` not found, so no symbols package. The package was **not installed or launched**: Windows Developer Mode is off on this machine (`AllowDevelopmentWithoutDevLicense = 0`), and installing an unsigned/test-signed MSIX needs either it or a trusted certificate, both of which need elevation. So MSIX *build* is verified; MSIX *install/run*, and `gist_ffi.dll` loading from inside a package, are **not**.
- The unpackaged run worked because Windows App Runtime 2.5.1 is already installed machine-wide here (`Get-AppxPackage`). An unpackaged framework-dependent app on a clean machine would need that runtime installed, or a self-contained build (`WindowsAppSDKSelfContained`), which was not tried.

## Decision
1. **Ship as a signed MSIX**, full-trust WinUI 3 desktop app (`runFullTrust`) with package identity. Identity gives clean install/uninstall, per-app data isolation and `ApplicationData` APIs, and is the closest thing on Windows to the Apple bundle plus sandbox.
2. **Capabilities: `internetClient` only** (URL import, ADR-005). **No `broadFileSystemAccess`.** All user files enter through `FileOpenPicker`/`FileSavePicker`; the core already copies on import (ADR-006), so it never needs standing access to the user's original.
3. **Data location:** package `LocalState` (`gist.sqlite3`, `storage/`, `originals/`), same layout as Apple's Application Support/GIST. Uninstall removes it, which is the intended behaviour and must be stated in the UI.
4. **Mapping to ADR-012:** app-sandbox ~ package identity/AppContainer-style data isolation; `user-selected read-write` ~ picker-only file access; `network.client` ~ `internetClient`. Caveat: a full-trust MSIX process is **not** an AppContainer sandbox. It runs with the user's token, and the manifest capability list is not an enforcement boundary the way the macOS entitlements are. Filesystem virtualisation of `LocalState` and the absence of requested broad capabilities are hygiene and policy, not containment. This is weaker than ADR-012 and must not be described as equivalent in the security review (`docs/security-review-windows.md`, W6). Encryption at rest (ADR-011/014) is therefore relatively more important on Windows; key custody via DPAPI/Credential Locker is a separate ADR.
5. **Dev inner loop is unpackaged** (`WindowsPackageType=None`): `dotnet build`/`dotnet run`, `gist_ffi.dll` copied beside the exe, no certificate, no Developer Mode. Anything that depends on package identity (`ApplicationData.Current`, pickers behaviour under identity, capabilities) must not be assumed to work in this mode; the storage path is injected (`GIST_STORAGE_DIR`-style) so the same code runs in both.
6. **Signing and distribution: decide at W6; both options stay open.**
   - *Microsoft Store:* Microsoft signs the package, no SmartScreen reputation problem for store installs, built-in update channel. Costs: a developer account fee (verify current figure and any individual/company differences), certification review latency and policy compliance, and an app that reads user documents plus a URL fetcher must clear review. Verify whether full-trust `runFullTrust` apps are accepted in the target account type.
   - *Signed sideload/direct download MSIX (or MSIX via a web `.appinstaller`):* full control of release cadence, but the publisher certificate must chain to a CA Windows trusts, and **SmartScreen reputation** for a new publisher can show warnings until it builds up (behaviour differs between OV/EV and cloud-signing options; verify current SmartScreen rules). Options to evaluate: an OV/EV code-signing certificate from a CA, or Microsoft's Trusted Signing (Azure) service. Prices, eligibility (geography/organisation age requirements) and hardware-token requirements for certificates have changed repeatedly and are **not stated here; verify at decision time**. Self-signed test certificates are for dev only and never committed (plan §Signing).
   - Track alongside F10 (release pipeline).
7. **CI:** a `windows-latest` job can verify: restore, `dotnet build` of the unpackaged and MSIX configurations, generating the (unsigned or test-signed) `.msix`, `dotnet test` for non-UI projects, and `dotnet list package --vulnerable`. CI **cannot** verify: real install/launch of the package (needs a trusted cert / developer mode on the runner; possible on an ephemeral runner but not yet attempted), UI behaviour, SmartScreen/Store certification, clean-machine runtime dependencies. Those stay manual W6 exit items. Not verified: whether the GitHub-hosted Windows runner image has the needed .NET 10 SDK and Windows SDK by default (check when the workflow is written).

## Consequences
- The team lead's W1 prerequisite "install the WinUI application development VS workload" is **not required to build**: SDK-style `dotnet build` worked without it. It is still useful for the XAML designer/Hot Reload/debugger experience and is optional, so W1 must not be blocked on it.
- The MSIX path needs a hand-maintained `Package.appxmanifest` and image assets (the spike built without them, but a store/sideload package needs real ones per `docs/iconspecification.md`), and a test certificate plus Developer Mode (or a trusted cert) on any machine that installs it.
- Loading `gist_ffi.dll` from an MSIX-packaged process, ARM64, and self-contained/clean-machine runtime behaviour remain unverified (see ADR-015's not-yet-verified list); they are W1/W6 exit items.
- Requiring elevation for Developer Mode is a one-time per-machine step to document in `SETUP_NOTES.md` (team lead).

## Addendum 2026-09-21 (W1 review)
- **Redistribution licence:** `Microsoft.WindowsAppSDK` is under proprietary Microsoft Software License Terms, not an OSI licence (`docs/THIRD-PARTY.md`). Its redistribution terms, especially for the self-contained option, must be reviewed before the MSIX release.
- **ARM64 is in scope for v1.0** (maintainer decision, review Q7). Decide before W6 whether to ship per-architecture MSIX packages or a bundle; the app currently defaults to `win-x64`, so an ARM64 build path (`-r win-arm64`) and an ARM64 runtime gate are required.
- Runtime choice (framework-dependent, needs Windows App Runtime 2.x, vs. self-contained via `-p:GistSelfContained=true`) remains open and unverified on a clean machine.
