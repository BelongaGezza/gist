# v1.0 release checklist (human-only)

Everything on this page needs a person with real credentials, a real device, or real users —
none of it is something an agent session in this dev environment can do. It exists so the next
step is a checklist, not a re-derivation of `CLAUDE.md`'s security register every time. Work
through it top to bottom; each section links back to the register row it's transcribed from,
so if something here looks wrong, that row is the source of truth to fix first.

## 0. Agent-side gate before tagging (decided 2026-10-04, M7 D7)

**v1.0 waits for M7** (`docs/m7-agent-roles.md`). The gate is M7's **R1** (the v1.0 library sort keys the spec promises — source type, date last read, progress — plus the `last_opened_at` schema change) and its **independent review (R-final)**. Not a gate, by decision (D6): real-document PDF quality — PDF layout remains tuned on synthetic files only, and `CHANGELOG.md`'s known limitations must keep saying so. Also open and unaffected by M7: the minimum-macOS question (D1 — the project builds for 26.5 while Q9 decided 14; decide after M7 R5's audit and before tagging, since it determines who can install v1.0).

## 1. Apple signing & notarization credentials

This dev environment has **zero** valid code-signing identities and no notarization
credentials configured (`security find-identity -v -p codesigning` → 0 valid identities;
confirmed 2026-09-28/29, see `CLAUDE.md`'s `F10` register row).

- [ ] Enroll in (or confirm access to) the Apple Developer Program, and obtain a **Developer ID
      Application** certificate (not a plain Development certificate — Developer ID is what
      Gatekeeper trusts for software distributed outside the Mac App Store).
- [ ] Export that certificate + private key as a `.p12` file, and choose a strong password for it.
- [ ] Create an App Store Connect **app-specific password** for the Apple ID that will run
      notarization (`xcrun notarytool` needs `--apple-id`/`--team-id`/`--password`, or an API key
      — this repo's `tools/notarize.sh` and `.github/workflows/release-macos.yml` expect the
      app-specific-password form).
- [ ] Configure these five GitHub Actions repo secrets (named exactly this, per
      `release-macos.yml`'s verify-secrets guard step):
      `APPLE_DEVELOPER_ID_CERT_P12`, `APPLE_DEVELOPER_ID_CERT_PASSWORD`, `APPLE_TEAM_ID`,
      `APPLE_ID`, `APPLE_APP_SPECIFIC_PASSWORD`.

## 2. Dry-run the release pipeline before trusting it

`release-macos.yml`'s unsigned half (xcframework build → `xcodegen generate` → `xcodebuild
build` → `tools/build-dmg.sh`) has been run for real in this dev environment and genuinely
works — see `CLAUDE.md`'s `F10` row for the exact commands and what was verified (a real ~16 MB
UDZO DMG, mounted and inspected). The signed half (archive → export → codesign → notarize →
GitHub release) has **never been run for real** — only written and reviewed against Apple's
documented tool invocations.

- [ ] After configuring §1's secrets, trigger the workflow once (either by pushing a real `v*`
      tag, or by temporarily adjusting the trigger to dry-run it another way) and confirm every
      step — archive, export, codesign, `tools/notarize.sh`, `gh release create` — actually
      succeeds, not just that the workflow file is well-formed.
- [ ] Staple the notarization ticket and confirm a downloaded, freshly-quarantined copy of the
      DMG opens without a Gatekeeper warning on a machine that has never seen this build before
      (a colleague's Mac, or a fresh VM — not this dev machine, which has already built and run
      unsigned copies).

## 3. `N8` — verify the signed Release build actually launches

Separate from whether the pipeline *runs* successfully: `CLAUDE.md`'s `N8` register row
documents a real, previously-shipped incident in a sibling app (contextGIST) where an
identically-shaped `gist-ffi`-style crate (`crate-type = ["staticlib", "cdylib", "rlib"]`)
silently linked the wrong artifact once Hardened Runtime was turned on for a real signed
Release build, and the app aborted at launch (`Library not loaded ... different Team IDs`).
GIST's current build path (`tools/build-core-xcframework.sh` selecting the `.a` by explicit
path, `embed: false` in `project.yml`) is believed to avoid this shape of bug, but **has never
been exercised under a real signed Release build with Hardened Runtime on** — only unsigned
Debug/CI-style builds.

- [ ] Do at least one real signed (not ad-hoc) Release build of `GISTmacOS.app` with Hardened
      Runtime enabled, launch it, and confirm there is no `Library not loaded` / library-validation
      error in Console.app or the crash log.
- [ ] **PDF / pdfium (added M6 R7, 2026-10-04):** the app now embeds a *separate* dynamic
      library, `Contents/Frameworks/libpdfium.dylib` (`project.yml`: `embed: true`,
      `link: false`, `codeSign: true`), which is exactly the artifact shape `N8` is about — the
      "gist-ffi links statically, so there is nothing to Hardened-Runtime-validate" argument no
      longer covers the whole bundle. In the same signed Hardened-Runtime Release build, import
      **a text PDF and a scanned (image-only) PDF** and confirm: (a) the text PDF imports (proves
      `libpdfium.dylib` loaded — a library-validation/Team-ID failure surfaces as the "PDF Support
      Unavailable" alert, not a crash), (b) the scanned PDF routes to the OCR sheet. Also run
      `codesign -dvvv --verbose=4 GIST.app/Contents/Frameworks/libpdfium.dylib` and
      `codesign --verify --deep --strict GIST.app` and confirm the dylib carries the app's Team ID
      (not ad-hoc / not the upstream linker signature), and that the entitlements do **not** contain
      `com.apple.security.cs.disable-library-validation`.
- [ ] **Windows CI (added M6 R7):** the `core-test` Windows leg — including its "no dynamic
      VC++ runtime imports" check on `gist_ffi.dll` (`tools/check-dll-imports.sh`) — and
      `windows-build` are green with the pdfium dependency tree (`pdfium-render`, `libloading`,
      `chrono`) present. This was not runnable from the macOS session that landed M6; see
      `docs/security-quality-review-2026-10-04.md` §6 for the specific risk.
- [ ] Do not refactor `tools/build-core-xcframework.sh` to `-l`/search-path linking as part of
      any future change — that's the specific pattern that caused the sibling app's incident.
- [ ] If `gist-ffi`'s `crate-type` ever drops `cdylib` (it appears unused by the shipped path),
      update `tools/verify-ffi-panic-swift.sh` in lockstep — it currently depends on the dylib.

## 4. Outstanding manual QA gates from M2 and M3 (predate M5, never closed)

These are not new to M5 — they've been open since M2 and M3 respectively, and no agent session
can close them in this environment (no Accessibility permission for `osascript`/System Events
here, so UI automation isn't possible; these genuinely need a person driving the app).
Shipping v1.0 without them means shipping without ever having had a person exercise these
paths — decide deliberately, don't let this happen by default.

- [ ] **M2:** a full manual click-through of sort/filter/theme/tags/collections/flow-view —
      tracked as `docs/qa-manual-clickthrough-m2.md`. Only one prior smoke-test pass exists
      (launch + render + import panel, 2026-09-12) — see `CLAUDE.md`'s M2 milestone-register row.
- [ ] **M3:** a live VoiceOver navigation pass, actually hearing the `AVSpeechSynthesizer`
      read-aloud feature speak, and eyeballing the Dynamic Type/contrast fixes on a real display
      — see `CLAUDE.md`'s M3 milestone-register row. The code-level accessibility work (contrast
      ratio fixes, label/trait fixes, Dynamic Type preview coverage) is done and tested; none of
      it has been confirmed by an actual screen-reader user or sighted click-through.

## 5. Public beta

- [ ] Recruit ~20–50 beta users (per `docs/development-plan-v2.md`'s M4/M5 scope). This document
      deliberately does not prescribe how or where — that's a product/distribution decision for
      you, not something to invent here.
- [ ] Decide where feedback gets triaged (a GitHub Projects board? A plain issues label? A
      spreadsheet?) before the beta starts, not after the first report arrives.
- [ ] Triage real feedback and fold anything release-blocking back into the milestone register
      in `CLAUDE.md` before tagging v1.0.

## 6. Tag and publish

- [ ] Once §1–§5 are genuinely done (not "written," *done*), push a real `v*` tag.
- [ ] Confirm `release-macos.yml` runs green on that tag, end to end, producing a real GitHub
      Release with the signed, notarized DMG attached.
- [ ] Update `CLAUDE.md`'s milestone register (M5 row) and `docs/development-plan-v2.md` to
      record the actual release, dated, the same way every other milestone closure in this repo
      is documented — with what was verified, not just what was intended.
