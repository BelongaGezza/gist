## 4. Findings

### F49: F44 is real in R2's tick loop, and R2 does the work for nothing. **Low** (Rust cost measured by R4; C# side reading-only)

- **Evidence:**
  - `FfiRsvpSession::frame_at_elapsed` (`crates/gist-ffi/src/lib.rs:907-934`) builds, on every call, `text: token.text.clone()` plus `orp: FfiOrpSplit::of(&token.text)`. That is an O(token-length) grapheme walk and three more copies.
  - R2's `FfiRsvpEngine.FrameAtElapsed` (`FfiRsvpEngine.cs:26-32`) maps only `f.Text`. `f.Orp` is never read (nor anywhere in `GIST.Core/Rsvp` or `RsvpPage`).
  - `RsvpReaderViewModel.RaiseAllDisplayChanged` (`RsvpReaderViewModel.cs:261-272`) raises 9 `PropertyChanged` events per controller `Changed`. `RsvpPage.OnVmChanged` (`RsvpPage.xaml.cs:127`) ignores the property name and runs the full `UpdateView`. Each run assigns `WordText.Text = vm.Word`. That is 9 text assignments and 9 layouts per tick.
- **Reasoning:** R4 measured 420 ms (release) for one `orp_split` over a 20M-character token. A document with one huge unbroken run, which the tokeniser and the 256 MiB txt cap permit, therefore stalls the UI thread for at least that long per tick, then hands a 20M-character string to a `TextBlock` nine times. Ordinary documents are unaffected (tokens are short, so the cost is tens of ns). This resolves R4's open question "how much this matters depends on R2's tick loop": it matters, but only for hostile or malformed input, and it is a local self-DoS.
- **Suggested fix:**
  - Add a lean accessor (or drop `orp` from the frame) so the Windows client does not pay for ORP it does not draw.
  - Cap or split over-long tokens in tokenisation, as R4 proposed.
  - Make `OnVmChanged` coalesce, or filter on a single property.

### F50: Engine faults outside `Guarded` crash or leak. **Low** (reading-only)

- **Evidence:**
  - `RsvpReaderViewModel.LoadAsync` (`:134`, `:141`) calls `engine.TokenCount` and `new RsvpPlaybackController(...)`, whose constructor calls `Refresh()` over FFI. Neither is inside a try/catch. A throw here escapes `LoadAsync` and so the `async void OnLoaded` (`RsvpPage.xaml.cs:62-89`, which just `await`s it), which is an unhandled exception in a UI event handler. The engine is also never disposed on that path.
  - `LeaveAsync` (`:174-185`) runs `c.Pause()` and then `Dispose()` with no `try/finally`. After `Guarded` has set `Failed` on a failing engine, the controller still has `IsPlaying == true`, so `Leave` re-invokes the faulting `engine.Pause`. The throw skips `Dispose`, leaving the `FfiRsvpSession` handle to the finalizer. `RsvpPage.LeaveAsync` swallows the exception, so nothing is surfaced.
  - The test `An_engine_that_throws_mid_read_stops_playback_and_reports_Failed_without_crashing` covers only the `Guarded` path, not leave-after-failure or load-time faults.
- **Reasoning:** the engine only throws on a core panic (`InternalPanic`) or a disposed handle, so reachability is low. But the code deliberately chose "an engine failure must never crash the shell", and these two paths are the exceptions to it.
- **Suggested fix:** wrap the post-open steps in `LoadAsync` in the same catch as `_openEngine`, disposing the engine on failure. Make `LeaveAsync` dispose in a `finally`. Add tests for both.

### F51: The W4 exit-criterion evidence is opt-in, partly tautological, and the cross-reference is dead. **Low**

- **Evidence:**
  - The soak test is `[SoakFact]`, which skips unless `GIST_RUN_SOAK=1`. The default run reports 1 skipped and nothing runs it in CI. I ran a 60 s version: it passes with lateness flat at ~8 ms mean, so the underlying behaviour is fine.
  - Its last assertion block (`RsvpSoakTests.cs:137-139`) is commented "Position tracks the clock: the last shown token must be the engine's answer for the wall time", but the code is `engine.FrameAtElapsed(0)` followed by `Assert.NotNull`, which proves nothing about position (the comment itself concedes "just sanity"). The real checks above it are the lateness bounds. They are meaningful but compare the controller against the engine's own schedule, not against an independent wall-clock expectation.
  - The timer is a thread-pool `Task.Delay` (the file says so), not the shell's `DispatcherQueueTimer`, so the UI-thread timing path is untested.
  - `docs/qa-manual-clickthrough-windows.md:128` says "measured numbers are in the W4 closeout in docs/windows-development-plan.md". That closeout does not exist in this tree. The plan still lists the RSVP reader as "done (drifting pacing)" at line 215, and the W4 exit line (`:186`) has no recorded result.
- **Suggested fix:** replace the final block with a real assertion (for example, the last shown index equals the reference answer for the final wall elapsed, within a tolerance). Record the 10-minute numbers in the W4 closeout, or reword the QA line. Consider running a short soak in the Windows CI job.

### F52: F34 is closed in the script, but its evidence is thin. **Low**

- **(a) Stamp re-hash. Closed, reading-only.** `fetch-pdfium.sh:153-167` re-hashes the on-disk dylib on a stamp hit, treats a one-line (pre-fix) stamp as a miss, and falls through to a full re-download on mismatch. The scope caveat in the script header is accurate and worth restating: the second hash lives in the same gitignored directory as the dylib, so a local writer who replaces both the dylib and the stamp line passes. It detects accidental corruption and a lone swap, not a determined local attacker. The archive's pinned `PDFIUM_SHA256` remains the only provenance anchor. Only the dylib is re-hashed, not `licenses/`, `LICENSE` or `VERSION`. That is acceptable, since nothing executable is loaded from them.
- **(b) Redirect hops. Closed, reading-only.** `curl … --proto '=https' --proto-redir '=https' --tlsv1.2` (`:175-177`).
- **(c) Pre-extraction listing. Closed, tested and reproduced.** `validate_archive` rejects absolute, `..`, drive-letter, UNC and backslash names, control characters, over-cap entry counts, and symlink, hardlink, device, fifo and socket entries. It runs after the SHA check and before any write. The 13-check test passed. The fixtures are hand-built ustar headers, so they exercise real `tar -t` and `tar -tv` output, and a sanity check proves the writer produces extractable archives, so "accepted" results are not artefacts. The tests are real, not tautological.
- **Gaps:**
  - No test exercises (a) or (b). The test only drives `--check-archive`.
  - Nothing in `.github/workflows/*` runs `test-fetch-pdfium-guard.sh` (grep: the workflows invoke only `fetch-pdfium.sh`). The guard can regress without CI noticing.
  - The test script is mode 100644, not executable (harmless: it is run as `bash …`).
- **Suggested fix:** add the guard test to `core-test` (it needs no network or macOS). If cheap, add a test that seeds a fake stamp and dylib, tampers the dylib, and asserts the script attempts a download (a `curl` shim on `PATH`).

### F53: The schedule cache key does not cover token content. **Info** (reading-only)

`ScheduleKey` covers config, token count and cursor, but not the token texts or kinds, while `RsvpSession.tokens` is `pub`. Replacing a token's text in place, with the same token count, would serve a stale cumulative table. Not reachable today: `FfiRsvpSession` exposes no token-mutation API, and `Core::new_rsvp_session` builds the stream once. The doc comment says the key "cannot drift", which holds for the config and cursor fields the callers actually assign but not for `tokens` content. Worth a one-line caveat in the doc comment.

**Memoised-vs-naive equivalence (R1 priority 1): confirmed.** Beyond R1's exhaustive static test, my 20,000-step random sequence of `seek`, `back_words`, `set_wpm`, `pause` and `resume`, with a warm cache carried across steps, produced zero divergences. The partition-point semantics match the naive `acc + dur > elapsed` scan, including the end-of-stream clamp.

### F54: Test-quality nits. **Info**

- `Back_five_words_while_paused_moves_back_by_exactly_five_words` (`RsvpRealEngineTests.cs:156`) asserts only `Frame.Index < 20`. The name promises "exactly five words". A real engine regression (back 1 or back 9) would pass. The scripted-engine test covers the counting rule, so the controller logic is covered, but the real-engine test does not do what its name says.
- `Saving_while_playing_is_throttled…` captures `var saves = _saved.Count` before the loop, so `Assert.Equal(1, saves)` is checked before the loop (it only proves the first tick saves). The throttle itself is correctly proven by `Assert.Single(_saved)` after 49 ticks.
- `A_failing_save_never_interrupts_reading` asserts the state stays `Ready` but not that the save is retried.
- **PENDING_APPLE_CHANGES item 4 is true.** `RsvpSession::seek`, `back_words` and `set_wpm` never add to `elapsed_at_pause`; only `pause` does (`gist-rsvp/src/lib.rs:395-438`). So a mid-play mutation that merely restarts the caller's clock loses the banked time from `stats_at_elapsed`. But no Rust test pins this (the controller's pause-first sequence is pinned only against the scripted fake's `PauseCalls`). If the Rust engine later starts banking in those mutators, R2's pause-first sequence would then double-bank, and nothing would catch it. Suggest one gist-rsvp test that asserts the current behaviour explicitly.

### F55: Catch-up has no ceiling. **Info**

By design (documented in the controller's drift model), `Tick` shows whichever token is correct for the measured elapsed time, however late. After a long UI-thread stall the reader jumps ahead without showing the skipped words, and the next periodic save records that position. The soak and real-engine tests exercise a 2 s late tick, not minutes. Consider auto-pausing when the lateness exceeds a threshold (for example a few seconds) so a stall does not silently consume the text. The same model exists in Apple's `RsvpWallClockEngine`.

### F56: WPM is not remembered. **Info**

`RsvpPage.OnLoaded` builds the view model without an initial WPM, so every open starts at `RsvpWpm.Default` (300), and a speed the user changed is lost on leaving. `Saved_progress_is_restored…` covers the position only. The UI spec does not require persistence, so this is a product call, not a defect.

## 5. Checked and found sound

- **Controller concurrency (R2 priority 2), reading plus tests:**
  - `DispatcherRsvpTimer.Cancel` clears `_callback`, so a stale queued `Tick` event is a no-op. `Schedule` stops and re-arms, so a re-entrant `Pause`/`Play` from a `Changed` handler cannot leave two live timers (the stale one cancels). `Tick` also re-checks `_disposed` and `IsPlaying`.
  - `Dispose` cancels the timer and disposes the engine, and `ThrowIfDisposed` guards every transport call. After the VM disposes the controller, the page has already unsubscribed.
  - `Mutate` is correct against `RsvpSession` semantics: pause (banks elapsed, pins cursor under the old speed), mutate at elapsed 0, resume, re-anchor. For `back_words`/`set_wpm`/`seek` the engine's `token_at_elapsed(0)` is the pinned cursor, so there is no double-count and no jump. `StepWords(int.MinValue)` is handled through `-(long)`.
  - The finish path banks elapsed time, stops on the last word (never blanks), and `Play` from the end restarts from 0.
- **Save-progress throttle:** first play saves immediately, then at most every 5 s, never the same index twice, forced on pause/stop/leave, and failures never interrupt reading. `SaveProgress` writes a SQLite row only, so it does not interact with R4's F39 orphan sweep (R4's note that W4 progress saving adds a writer to the sweep race does not apply: the sweep only deletes blob files).
- **VM lifecycle:** `LeaveAsync` runs once (the page's `_left` guard covers the double `OnNavigatingFrom`/`OnUnloaded` entry). A load that completes after the page is gone disposes the engine. Handle ownership is clear: the caller of `OpenRsvpEngineAsync` disposes, and the engine is independent of `CoreClient`'s lifetime.
- **FFI surface (R1):** all 20 `pub fn` in `impl FfiRsvpSession` plus `rsvp_orp_split` are `ffi_catch!`-wrapped (counted: 20/20). Locking is poison-tolerant. Client `u64` goes through the saturating `ffi_index`. `frame_at_elapsed` does a single lock for index, boundary and text, so the frame is internally consistent. `open_rsvp_session` clamps WPM and shares `Core::new_rsvp_session` with `start_rsvp` (the JSON contract is pinned by a test, and `schedule` is `#[serde(skip)]`).
- **R4's F43** (`pause` unchecked add) is unreachable from R2: elapsed comes from `Stopwatch`, which cannot approach `u64::MAX`.
- **R3 assets and icon code:** the ICO and tiles verify byte-for-byte as claimed. `SetWindowIcon` is best-effort, uses `AppContext.BaseDirectory`, and the csproj copies the icon. `generate-assets.ps1` derives its paths from `$PSScriptRoot` and has no absolute paths.
- **`tools/fetch-pdfium.sh`:** see F52. No regression to the pinned tag or hash.
- **Cargo and licences:** `gist-ffi` gains `gist-model` (already a workspace crate); `criterion` and `serde_json` are dev-only. `cargo deny` is clean.
