# GIST — Claude Code Context

GIST is a cross-platform RSVP-style reading app. The Rust core handles all parsing, persistence, and pacing logic; native UI shells (SwiftUI on macOS/iOS, WinUI 3 on Windows) call into it via FFI.

## Platform awareness (read first)

- **This repo is developed on several machines** (macOS M1 Pro, Windows 11, possibly Linux). A `SessionStart` hook (`.claude/settings.json` → `tools/detect-platform.sh`) prints a `[GIST ENV]` block at session start giving the current OS, buildable targets and missing tools. **That block is the only source of truth for the current machine.**
- **Every machine-specific statement in this file is historical**, written from the macOS session (Xcode version, "no Accessibility permission", "verified locally", "this dev environment"). Treat them as `[verified: macOS/M1, <date>]`, not as facts about the current machine. Record new verification results per platform in `PLATFORM_VERIFICATION.md`.
- **Architecture precedence:** this repo is a Rust core with native shells (SwiftUI, WinUI 3). Any parent-directory CLAUDE.md that describes a Flutter/Dart architecture does not apply here; where they conflict, this file wins. The parent's platform-guard, no-absolute-paths and cross-platform-check rules still apply.
- **Non-macOS sessions may not edit Apple code** (`apps/apple/**`, `ios/`, `macos/`, Xcode projects, entitlements, `Info.plist`). `tools/guard-apple-edits.sh` (a `PreToolUse` hook) is a best-effort safety net that blocks most such Write/Edit calls (not Bash-tool edits); the real enforcement is CODEOWNERS and PR review. Log the needed change in `PENDING_APPLE_CHANGES.md` instead; set `GIST_ALLOW_APPLE_EDITS=1` only when the user explicitly instructs the edit.
- **Handoff files:** `PENDING_APPLE_CHANGES.md` (Apple work deferred from other OSes), `SETUP_NOTES.md` (per-machine setup), `PLATFORM_VERIFICATION.md` (what is verified where). Update them in the same commit as the change they describe.
- **Reverse handoff:** `PENDING_WINDOWS_CHANGES.md` (heading `## Pending Windows Change`) records Windows-only work (`apps/windows/**` C#/XAML) that was edited or needs verifying from a session that could not build it. On Windows/Linux sessions `detect-platform.sh` flags unapplied entries; delete each entry once applied and verified.
- **macOS sessions may edit `apps/windows/**` as text, with a warning only:** `tools/guard-windows-edits.sh` (a warn-only `PreToolUse` hook, always exit 0) reminds you the code cannot be built or tested on macOS; log what needs Windows verification in `PENDING_WINDOWS_CHANGES.md`. `GIST_FAKE_OS` is a test-only seam in both scripts; leave it unset.
- Hook scripts are bash and run under Git Bash on Windows. Do not use `python3` in scripts (the Windows Store stub hangs).

## Key architectural decisions (ADRs in docs/adr/)

| ADR | Decision |
|-----|----------|
| 001 | FFI = uniffi proc-macro mode (not hand-rolled C ABI) |
| 002 | PDF backend = `pdfium-render` behind a swappable trait |
| 003 | Annotation anchoring: `(block_id, start, len, prefix_hash, quote_hash)` |
| 004 | DRM: detect via `META-INF/encryption.xml`; never circumvent |
| 005 | Web fetch: TLS-only via rustls, max 5 redirects, robots.txt |
| 006 | Copy-on-import (not reference-in-place) |
| 007 | IR storage: `<id>.json` + `<id>.tokens.json` on disk; SQLite holds metadata |
| 008 | FTS5: external-content table + tokens shadow table + sync triggers |
| 009 | OcrEngine: uniffi callback interface (Swift implements, Rust orchestrates) |
| 010 | HTTP: ureq + rustls (no tokio, no system OpenSSL) |
| 011 | Encryption at rest: AES-256-GCM at `gist-store`'s file boundary, platform-backed `KeyProvider` |
| 012 | macOS app sandbox (entitlements) |
| 013 | At-rest integrity: BLAKE3 checksum sidecar files, verified on read, missing = unverified not corrupt |
| 014 | Per-item on-demand encryption (`Store::encrypt_item`), plus decoupling read-decrypt capability from write-auto-encrypt behavior (`Store::open_with_read_key`) |
| 019 | IR/schema versioning: `ir_version` envelope at the `gist-store` storage boundary (not on `gist_model::Document`); forward-compat rejection (`StoreError::IrVersionTooNew`) mirrors `SchemaTooNew`; additive changes need no version bump |
| 021 | Reading-state model: schema v7 `library_items.last_opened_at` (stamped by both readers via `mark_item_opened`), progress derived from the RSVP `reading_progress` position (flow-only items show 0%), `source_type` exposed, index `idx_tokens_item_idx` |
| 022 | PDF parser process isolation (`F33`): options and measured spike; recommendation to accept for v1.0 and schedule a portable helper process later — pending user decision |
| 023 | Paginated reading view: pure `Paginator` over AppKit-measured line fragments, position stored as a (block, offset) anchor in its own store |

## Independent security audit (2026-09-12, main @ 59cff8c)

An independent consultant audit of the Rust core, import pipelines, FFI boundary, and CI/supply-chain posture landed same-day as the collections/search/URL-import/removal/copy-on-import work above. Findings are tracked as `F14`–`F25`/`A6`–`A7` in the security register below. The two High findings were fixed same-day:

- **`F15` ✅ Closed 2026-09-12.** `gist-parse-epub`'s DRM/container-metadata reads (`container.xml`/OPF/`encryption.xml`) had no `max_expanded_bytes` cap, unlike spine content — a zip bomb targeting those three files worked against the shipped import path. Fixed: `check_drm`/`read_zip_entry_string` now route through a shared `read_capped` helper capped at `MAX_METADATA_EXPANDED_BYTES` (4 MiB), independent of `ParseLimits.max_expanded_bytes`. Covered by two new tests building a synthetic compression-bomb zip targeting each of `container.xml` and `encryption.xml`.
- **`F14` ✅ Closed 2026-09-12.** `gist-web::fetch_url` only checked `scheme() == "https"`, never the resolved IP — SSRF via a DNS-controlled domain resolving to loopback/RFC1918/link-local. Fixed: `build_agent()` now sets `.https_only(true)` and `.resolver(safe_resolve)`, where `safe_resolve` filters out non-globally-routable addresses (loopback/private/link-local incl. cloud metadata/multicast/broadcast/documentation/unspecified/RFC 6598 CGNAT, plus IPv4-mapped IPv6 and IPv6 unique-local/link-local). Both are enforced by `ureq` on every connection attempt including redirect hops, which as a corollary also closes **`M-1`** (redirects weren't re-validated per-hop) — no separate fix was needed for that half of the finding. Covered by new unit tests on the address filter and `safe_resolve` itself.

See the security register for the full list, and `docs/development-plan-v2.md` §0/§5/§8 for milestone scheduling.

## Security policies — must not be relaxed

All are enforced in code (M1 ✅). See `docs/security-review-v2.md` for full detail (supersedes v1).

- **FFI panic safety:** every `#[uniffi::export]` function is wrapped in `catch_unwind`. Panics map to `GistError::InternalPanic`, never propagate across the C ABI.
- **Mutex discipline:** all `gist-store` lock acquisitions use poison-tolerant recovery (`.unwrap_or_else(|p| p.into_inner())`).
- **ParseLimits:** every parser accepts a `ParseLimits` struct and enforces `max_bytes`, `max_pages`, `max_nesting_depth`, `max_expanded_bytes` before allocation.
- **DRM:** `gist-parse-epub` detects DRM via `META-INF/encryption.xml` and returns `ParseError::DrmProtected`. No decryption is ever attempted.
- **Supply chain:** all GitHub Actions pinned to immutable commit SHAs. `cargo-deny` blocks on RUSTSEC advisories. License allow-list: MIT/Apache-2.0/BSD/ISC/Zlib/Unicode-3.0 plus MPL-2.0 (file-level copyleft only, allowed because it's required transitively by uniffi per ADR-001 and by scraper per ADR-005 — not optional). `cargo deny check bans licenses sources` is verified green locally. **Update 2026-09-19: `cargo deny check advisories` is functional again in CI, and now genuinely clean.** `.github/workflows/core-quality.yml`'s `cargo-deny-action` was bumped to v2.1.1 (bundles cargo-deny 0.20.2 in its own Docker image, independent of host rustc), which parses the CVSS 4.0 advisory entries that 0.18.3 couldn't. This local dev environment's own `cargo-deny` binary is still 0.18.3 and still can't run `check advisories` locally (upgrade it locally with `cargo install cargo-deny --locked` if you need to run it outside CI). Running for real for the first time immediately found 7 previously-invisible RUSTSEC advisories, all fixed same day (`quick-xml`/`ureq` upgrades, `scraper`'s already-planned bump, one license-allow-list addition) — see `N7` in the security register for the full breakdown. `core-quality` is fully green on real GitHub Actions for the first time in this project's history.
- **Document IDs:** UUIDv7 (not timestamps).
- **Schema migrations:** transactional; version ceiling check (`SchemaTooNew`).
- **Source paths:** logged at `debug!` level only, never `info!`.
- **Copy-on-import (ADR-006):** implemented 2026-09-12. `gist-store::store_original_copy` writes a SHA-256-content-addressed copy of file-based imports to `<storage_dir>/originals/`; `Metadata.source_copy_ref` points at it. `remove_items(delete_source_files: true)` deletes that copy — never `source_ref`'s raw path (the user's real file, wherever it lives). URL imports have no copy (nothing local to copy); `source_copy_ref` stays `None` for them.

`List(selection:)` multi-select with a toolbar Delete button and a confirmation alert offering "Remove from Library" (`deleteSourceFiles: false`) vs "Also Delete Original File" (`true`), styled like the existing DRM alert; a toolbar "Import URL" button opening a text-entry alert that calls `core.importUrl`; and a minimal toolbar "Add to Collection" menu, populated from `core.collections` (fetched via `.task` on appear), that adds the current selection to an existing collection or creates one first via a "New Collection…" alert. **Two bugs found and fixed 2026-09-12 (user-reported), both the same underlying trap wearing different clothes.** First: the initial cut of this UI wrapped every row in `NavigationLink(value: item.id)` *inside* the selectable `List` — on macOS a full-row `NavigationLink` swallows the click as a navigation push, so `selection` could never become non-empty and the toolbar Delete button could never enable; clicking a book to select it for deletion instead launched the reader. First fix attempt: made rows plain content (so `List`'s native click-to-select works) and added `.onTapGesture(count: 2)` per row to open the book on double-click, routed through a `navigationPath: [String]` that `ContentView` now owns and passes down as a `@Binding`. User confirmed the new right-click → "Remove…" context-menu item worked — but then reported the toolbar itself still showed no way to select/delete anything. ## Crate conventions

- No `unwrap()` on parsed/external data. Use `?` or `unwrap_or_else`.
- No bare `.lock().unwrap()` in `gist-store` — always poison-tolerant.
- Every `#[uniffi::export]` fn body wrapped in the `ffi_catch!` macro (defined in `gist-ffi`).
- `source_ref` paths at `debug!` level only.
- `gist-model` must compile to `wasm32-unknown-unknown` (no I/O deps). **Correction 2026-10-04:** this was false until M6 R7 — `uuid` v7 needs an RNG source on that target; fixed by a wasm32-only `uuid` `js` feature in `gist-model/Cargo.toml` (native builds and `Cargo.lock` unaffected). `cargo check -p gist-model --target wasm32-unknown-unknown` now passes.
- Document IDs: `Uuid::now_v7().to_string()`.
- `ParseLimits` passed to every parser — never skip limit checks.

## Independent re-verification pass (2026-09-18) — `docs/security-review-v2.md`

A second-pass security review re-derived every `F14`–`F25`/`A5` closure claim above directly from the current source rather than trusting this file's log, and actually re-ran `cargo test --workspace`/`clippy -D warnings`/`fmt --check`/`cargo deny check bans licenses sources` fresh in-session (all still genuinely green) plus `cargo deny check advisories` (still genuinely fails with the documented CVSS 4.0 parse error). **Every prior closure claim held up against the code.** It also found four new items not previously tracked, now folded into the register below as `N1`–`N5`:

- **`N1` (Medium, open):** the fuzz-testing harnesses (`fuzz/fuzz_targets/*.rs`) do not currently compile — independent of cargo-fuzz being absent from this dev environment. All four targets construct `gist_model::ParseLimits` with a struct literal missing the `max_zip_entries` field added by `F16` (no `#[non_exhaustive]`, no `..Default::default()`), an unconditional `E0063`. Separately, `fuzz/Cargo.toml` has no `[workspace]` table and isn't excluded from the root workspace, so even a fixed literal would hit "current package believes it's in a workspace when it's not" the moment `cargo fuzz build`/`cargo check` runs inside `fuzz/`. Net effect: none of the `F15`–`F17` parser hardening has actually been fuzzed since `F16` landed on 2026-09-12, only unit-tested.
- **`N2` (Low, open):** `fuzz_web_extract.rs` only fuzzes `gist_web::fetch_url` with fuzzer bytes reinterpreted as a URL string (per its own TODO comments) — it never reaches `extract_content`/`collect_text`, the HTML/DOM-recursion code `F17`'s depth cap actually lives in. That fix has zero fuzz coverage, only its two unit tests.
- **`N3` (Low, open):** `gist-parse-docx`'s `read_zip_entry_limited` enforces `max_expanded_bytes` fresh per call (styles.xml, numbering.xml, document.xml each get the full budget independently), unlike `gist-parse-epub::parse_spine`'s shared accumulator across all spine items — a crafted DOCX could expand to ~3× the intended per-document ceiling before any part individually trips the cap.
- **`N4` (Medium, dormant, open — sharpens `A7`):** `gist-imageprep::prepare_image` calls `image::load_from_memory` (full decode) *before* checking the decoded pixel count against `limits.max_expanded_bytes / 4` — the exact decode-before-check pattern `F15`/`F16` fixed for zip formats, not yet fixed here. Dormant today only because `Core::import_image_with_ocr` is still `todo!()` with no caller reaching this function; must be fixed as part of `A7`'s work, not deferred further, since `M3` will wire a live caller straight into this gap.
- **`N5` (Informational, open):** `Cargo.lock` is tracked in git despite being listed in `.gitignore` under a stale "library crates" comment — harmless (committing it is in fact the right call for an application repo, and cargo-deny's checks depend on it), but the ignore file should be corrected to match actual practice rather than contradict it.
